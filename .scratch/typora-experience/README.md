## 主要发现

| 方面 | Inkora 当前事实 | Typora 本次观察 | 优化意义 |
| --- | --- | --- | --- |
| 正文 | 16px/1.65；可视区使用系统无衬线；普通标题、段落、列表、引用、行内代码缺少统一显式排版规则 | 标题层次、标题分隔线、段落留白、引用左线、行内代码底色形成连贯阅读样式 | 先建立完整文档排版，不逐个局部美化 |
| 阅读宽度 | 右侧大纲统计常开；编辑器 padding 按整个 viewport 计算 | 本次左侧大纲与正文各自成区 | 按可用正文容器计算行宽，避免侧栏和留白重复扣宽 |
| 工具占位 | 查找入口与模式/插入行常驻；表格 11 个操作按钮、代码语言/许可栏常驻 | 本次未聚焦表格/代码时没有同类常驻按钮组 | 操作可发现性、键盘入口和阅读安静程度需要共同设计 |
| 代码块 | 已有独立背景、边框、内边距、等宽字体与离线语法高亮 | 代码块与正文形成轻量区分 | 优化工具栏和整体节奏，不将已有能力误记为缺失 |
| 数学与图表 | 公式为保护源码卡片；Mermaid 为代码文本 | 实际看到公式排版与 flowchart 图形 | 真渲染需要单独能力切片，CSS 不能完成 |
| 脚注 | 引用保留原始语法，定义为保护卡片 | 引用/定义具有专门呈现与返回入口 | 与通用保护片段边界一起设计，不能用隐藏原文伪装实现 |
| 图片 | 自有 fixture 尚未向 Sandbox 授权，显示授权占位 | 同一图片直接显示 | 本次不足以判断 Inkora 图片渲染缺陷；不为比较而扩大授权 |

布局推断有源码依据：`#editor` 的水平 padding 为 `max(32px, (100vw - 760px)/2)`，右侧展开面板宽 264px。按这些规则计算，在 900px 和 1080px 窗口中，扣除侧栏及 padding 后均可能仅余约 496px 正文。这里是 CSS 算式推断，不是已匹配视口后的实测数值。

## 拟议推进顺序（不是已批准任务）

1. **正文排版与可用行宽**：统一标题、正文、列表、引用、行内代码、表格、代码块；正文宽度依赖实际容器，覆盖有/无侧栏及宽/窄窗。交付真实 App 同文档对照，不只提交 CSS。
2. **低干扰操作界面**：按用户决定调整大纲/统计/模式/查找入口与上下文工具。工具通过键盘仍可达，工具持焦时不自行隐藏；显隐不引起正文跳动，也不抢 composition 焦点。查找、链接、表格、图片和语言选择功能继续可用。
3. **更丰富的技术表达**（若纳入）：公式、Mermaid、脚注各自形成完整纵向切片，离线本地渲染，保留原文、诊断、源码修复和失败回退；先评估既有 parser provenance/保护节点接缝，再提出明确依赖，不引入第二套语法权威。

实施规格需明确：默认展示状态、快捷键与入口、焦点/选区守卫、渲染失败样式，以及不同内容的编辑与预览切换方式。规格和任务不应复制当前保护卡片作为“效果已完成”的验收结论。

## 后续验收原则

- 同一 fixture、匹配窗口尺寸、相同内容位置对照；记录浅/深色与宽/窄窗，并保存可复核截图。对照前不擅自更改用户 Typora 偏好。
- 排版调整不改变 exact raw、dirty、revision、选区或历史；上下文操作继续走已有公共 runtime/DOM 接缝。
- 自动化验证只覆盖新交互的实际风险，避免为纯 CSS 细节写镜像测试；最终仍在真实 WK App 查看效果。
- 新内容渲染需同时验证正常、非法/未闭合、过大内容和离线失败，不把 HTML/SVG 执行或网络加载当快捷实现。
- 用户提出具体反例时才安排必要的人工输入；不循环要求已拒绝的重复 IME 流程。
