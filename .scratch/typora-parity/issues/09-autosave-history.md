# 确定自动保存与历史版本的职责边界

## Question

在现有独立恢复草稿和显式保存的基础上，哪些阶段需要原文件自动保存及可浏览的历史版本？三者如何分别处理未命名文档、外部修改、只读、保存失败及关闭时用户选择，避免把恢复草稿误当文件已保存或已有版本历史？

## Resolution criteria

用户确认各能力的职责、启用规则、冲突/恢复行为与阶段归属；系统版本 API 或自建方案涉及的事实不足时再建立研究票。沿用保真和原生文件状态规则，结果不构成自动更新或云同步承诺。

## Evidence

[技术写作基线研究](01-writing-baseline.md) 已核实现有恢复草稿、关闭的 autosavesInPlace 与缺失的版本浏览入口。

本次另核对产品主干 `36e636578798510d240b23520122c88578cf3fe5` 的 InkoraDocument/RecoveryStore/RecoveryCoordinator：原位自动保存仍关闭；恢复捕获有独立写入路径，恢复提示将内容恢复为未保存副本；原生保存检查原件状态并按成功快照确认保存。上述是代码读取证据，不代表本次实际运行或所有失败场景已验收。

## Answer

2026-11-08，管理者按用户“后续按照你的建议进行选择”的授权采用下列推荐，未冒称用户逐条回答。本票解决职责、产品行为和阶段归属，不提前采纳未核实的平台API方案。

### 首阶段保留显式保存，完善独立恢复

- 首个可交付写作阶段使用显式保存原文件，保留并完善默认启用的独立恢复草稿；不在该阶段顺带开启原位自动保存或承诺版本浏览。恢复草稿成功写入不清除dirty、不更新原文件保存点，也不显示“文件已保存”。
- 恢复范围包含当前原文及关联的待移交托管资源。含混/未安全支持的结构化内容仍可作为有状态标记的原始恢复草稿保存，不能因结构化保存被阻断就丢掉用户缓冲；重开继续标明待修复状态。不支持的编码只读窗口不产生伪造的空白编辑草稿。
- 后台恢复捕获不移动焦点、不强制提交composition。恢复已提交的输入；尚未上屏的系统候选不冒称已经持久化。恢复失败明确提示并保留内存编辑与待移交图片，不误报保护已完成。
- 重启后先提供恢复/另存为/明确放弃的入口，恢复为未保存副本，不自动覆盖原件。源文件已变化、丢失或失去权限时保留原件与草稿分别处理；不自动合并冲突。
- 成功保存及正常放弃后的恢复清理以最新提交状态、草稿/图片所有权为准，不能删掉保存期间新产生的修改或其它文档资源；资源规则沿用[本地图片政策](06-local-assets.md)。

### 原文件自动保存与可浏览历史纳入后续文件工作流阶段

两项都属于完整对标路线，安排在首阶段写作与文件资源闭环之后的文件工作流阶段；具体阶段序号由[阶段分组票](08-stage-sequence.md)统一命名。不能无限期留为可选愿景，也不挤入当前M0内核原型。

原文件自动保存采用应用级明确开启，初始默认关闭；按文档显示可用、暂停或失败状态。开启后仅对已由用户命名并具备有效权限、无原件冲突、内容与资源均具保存资格的文档工作。未命名文档先保留恢复草稿，首次文件位置由用户明确选择，不能自行创建猜测路径。

后台写原件必须复用显式保存的保真、权限、冲突、资源提交与快照确认契约：先保存资源，再确认对应文档快照；新修改发生在保存期间时仍保持dirty。合并频繁请求，在编辑稳定后触发，不每键全量写盘，不用修改用户输入法状态来取得快照；具体时机与负载由性能测量支持，不承诺未经测量的固定间隔。

首次向用户开放自动写原件时，同阶段必须提供可理解、可实际恢复的历史入口。历史也可记录显式保存产生的有效检查点，不要求用户先开启自动保存。恢复历史前保留当前未保存内容，先展示版本或恢复为副本；覆盖当前原件须用户明确执行，不能因点选历史条目就覆盖。

### 关键场景

| 场景 | 行为 |
| --- | --- |
| 已命名、可写且无冲突 | 显式保存或用户已开启的自动保存可提交合格快照；只有成功的对应快照更新文件保存点，恢复草稿另行维护 |
| 未命名/首次保存取消 | 不自动挑路径；继续dirty，保留原文和草稿图片，关闭仍按未保存文档处理 |
| 外部修改/删除/权限失效/只读 | 暂停自动写原件，保留本地编辑和恢复草稿；提供重新授权、重新载入或另存为等适用入口，不静默覆盖或清空 |
| 保存失败/磁盘满/资源复制失败 | 不markSaved、不清理仍需要的恢复资源，不无限重试弹框；明确失败状态，用户可重试或另存为 |
| 结构化保存不安全 | 不自动整篇切源码，不自动写原件；保留原文恢复副本，等待主动修复或Undo |
| 关闭时有未持久化编辑 | 保留保存/放弃未保存改动/取消的清晰选择；保存失败不关闭。已自动保存的改动属于文件历史，不能把“放弃未保存改动”误称可撤回已写盘内容 |
| 版本恢复 | 保留当前未保存缓冲，提供只读查看/比较或恢复为副本；用户明确替换时仍经过普通保真/权限/冲突/资源保存流程 |
| Undo/Redo | 属于当前编辑会话；不以恢复草稿次数或文件历史条目充当Undo步骤，自动保存本身不增加正文编辑步骤 |

### 历史的资源与存储约束

文档版本保存原始Markdown字节及所需的资源关联。仍被保留历史引用的托管资源不能被本应用清理；已有外部图片引用继续保留原始路径，不能暗示已授权并冻结任意外部文件。资源缺失或外部变化要如实显示，不静默改历史引用。

不默认备份每次按键，不无限增长，不清理来源文件或无所有权资源。版本检查点触发、容量/保留策略、应用卸载/迁移以及系统版本API与自建存储的取舍，需要[平台事实与方案研究](16-save-history-platform.md)核实，再由后续决策票定案；研究不使本票的职责和安全边界失效。

### 验收与后续交接

首阶段必须证明：恢复草稿不覆盖原件、恢复副本含正确字节/托管资源、失败/取消/冲突不丢编辑、composition不被后台捕获打断。后续阶段必须另外证明：自动保存资格/暂停状态、并发快照、故障恢复、真实历史浏览/比较/恢复及资源保留；按[质量门槛](07-quality-gates.md)分别记录模型、真实磁盘、Sandbox、WKWebView与系统IME证据。

本票只完成产品政策；没有启用生产autosavesInPlace、修改任何保存代码或运行产品测试。当前M0与首阶段功能仍需各自规格和实施，研究后才选择具体版本API与存储方案。
